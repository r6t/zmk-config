# ZMK Keyboard Configuration

ZMK firmware config repo for a personal ortholinear keyboard family. All boards run the same keymap design. Load the `zmk-keymap-builder` skill for detailed layer specs and workflows.

## Rules

- Only modify files that are part of this repo's git project. For files outside this scope needing modification, tell me what to change and let me do it. One exception: you can `mkdir` in `/tmp` and use any directories you created in `/tmp` for things like cloning git repos to inspect.
- The sister repo at `~/git/blank-slate-zmk-config` is **outside this scope**. Never edit, commit, or push there. If changes are needed there (e.g. to port a keymap update), describe the changes and let me apply them.
- Never run `git add`, `git commit`, or `git push` under any circumstances, in any repo.
- Never run `west build`, `west update`, or any local firmware build commands. Builds are owned by GitHub Actions on push.

## Scope of This Repo

This repo builds firmware for boards that ZMK's `main` branch supports cleanly: **helix, helix_4row, planck**. ZMK `main` tracks Zephyr 4.1 / HWMv2.

## Sister Repo: blank-slate-zmk-config

The Blank Slate lives in a **separate repo** at `~/git/blank-slate-zmk-config` (fork of `petejohanson/blank-slate-zmk-config`). It is pinned to ZMK `v0.3` (pre-HWMv2) because the upstream `blank-slate-zmk-module` HWMv2 migration is unmerged in upstream; v0.3 is the only ZMK revision that produces firmware that flashes correctly to this hardware today.

The Blank Slate is a 4-row one-piece 40% wireless ortho — same form factor as planck and same layout as our other 40% boards. Its keymap (`config/lpgalaxy_blank_slate.keymap`, HWMv1 board name) follows the same parity rules described below. Don't try to merge the Blank Slate into this repo until upstream's HWMv2 PR is merged and validated.

## When to use a separate ZMK config repo

Add a new board to **this** repo if:
- ZMK `main` has a working board definition for it (upstream board or shield), or
- The board is a custom split shield we can fully define ourselves (like `helix_4row`)

Add a new board to a **separate** repo when:
- The board lives in an external ZMK module that's only validated against an older ZMK release, or
- The board's bootloader/partition setup conflicts with ZMK `main`'s expectations and the upstream module hasn't migrated

Each ZMK config repo can only pin to one ZMK revision in `west.yml`, so mixing main and v0.3 in one repo is not possible.

## Keymap Philosophy

- **Reference design:** `config/helix.keymap` (5-row split 50%) is the gold standard.
- **4-row parity rule (the central rule):** The bottom 4 rows are byte-identical in function across ALL boards on ALL layers — same keys, same `&trans` placements, same numpad ordering. The only difference between 50% and 40% is whether the bonus row exists at all. 50% adds a row on top; 40% does not. Never remap or shift content between board sizes. This rule applies to the sister repo's blank_slate keymap too.
- **50% bonus row:** The top row on 50% boards gives direct access to numbers (Layer 0) and F-keys (Layer 1). On 40% boards there is no number row on Layer 0 — numbers come from the RAISE-layer numpad. F-keys on 40% live on Layer 1 row 1. The bonus row on 50% boards is `&trans` on Layers 2 and 3.
- **Simple bindings only:** `&kp`, `&mo`, `&bt`, `&out`, `&soft_off` — no hold-tap, combos, or macros unless explicitly requested.

## Layer Design Notes

- **LOWER** (`&mo LOWER`, home row col 0): symbols, F-keys (50% bonus row), media/nav/brightness controls.
- **RAISE** (`&mo RAISE`, bottom row col 7): full numpad on right side (no number-row substitute on 40% — numbers come from the numpad). No BT/output bindings.
- **ADJUST** (hold LOWER + RAISE simultaneously): F1–F12 on the top row, BT profile management on the ZXCV row, `&soft_off` + `OUT_BLE`/`OUT_USB` on the bottom row. Identical layout on all boards.
- **Power / sleep:** All wireless boards: `CONFIG_ZMK_SLEEP=y` (auto deep sleep after 3h), `CONFIG_ZMK_PM_SOFT_OFF=y`. `&soft_off` on ADJUST bottom row col 0 with `hold-time-ms = <500>`. Any keypress wakes from sleep/soft-off. Planck is USB-only — no sleep config, no soft-off.
- **Reset / bootloader:** All keyboards have a physically accessible reset button. Single tap = reset, double tap = bootloader (DFU). No keymap bindings needed or used for this.
- **No stuck layers:** all layer keys use `&mo` (momentary). No `&to`, `&tog`, or `&sl`.

## Active Profiles (in this repo)

| Shield/Board | Form | Type | Custom shield? |
|---|---|---|---|
| `helix` | 5-row split 50% | Reference | No (upstream ZMK) |
| `helix_4row` | 4-row split 40% | Planck-like | Yes — `boards/shields/helix_4row/` |
| `planck` | 4-row one-piece 40% | USB-only legacy | No (upstream ZMK) |

Sister repo (`blank-slate-zmk-config`) handles `blank_slate` (4-row one-piece 40%, wireless, Planck-compatible).

Each profile has `config/<name>.conf` and `config/<name>.keymap`. Build targets are in `build.yaml`.

## Custom Shield Pattern

When a board needs a non-standard matrix (e.g. `helix_4row`), create a custom shield under `boards/shields/<name>/` containing `Kconfig.shield`, `<name>.dtsi`, and `<name>_left.overlay` / `<name>_right.overlay`. Upstream shields (helix, planck) are provided by ZMK.

## Workflow Rules

1. Any new build target must be added to `build.yaml` (this drives the GitHub Actions matrix).
2. When modifying any keymap layer, audit parity across all active profiles and port changes consistently. If the change affects the universal 4-row design, also port to `~/git/blank-slate-zmk-config/config/lpgalaxy_blank_slate.keymap` (note: HWMv1 board name there).
3. Board ID syntax (ZMK Zephyr 4.1): `nice_nano//zmk` (v2, used for all wireless boards), `planck//zmk`.
4. Standard wireless `.conf`:
   ```properties
   CONFIG_BT_CTLR_TX_PWR_PLUS_8=y
   CONFIG_USB_HID_POLL_INTERVAL_MS=1
   CONFIG_ZMK_SLEEP=y
   CONFIG_ZMK_IDLE_SLEEP_TIMEOUT=10800000
   CONFIG_ZMK_PM_SOFT_OFF=y
   ```
5. Before attempting to add a new external module board, verify the module has been tested against ZMK `main`. If it's only validated on a specific ZMK release, build it in a separate config repo pinned to that release.
